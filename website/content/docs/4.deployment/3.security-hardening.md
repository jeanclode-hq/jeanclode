## Overview

JeanClode runs AI agents that read your code and interact with GitHub/GitLab/Sentry. Because agent behavior is driven by external content (which may contain prompt injection attempts), defense in depth matters.

## Credential Proxy

Every agent subprocess runs behind a built-in credential proxy that injects API keys and Git tokens into outbound HTTP traffic. The Claude process itself never receives raw credentials. This runs automatically, there is nothing to configure.

### Logging in to web apps from a skill

A skill can have the agent log in to a web app (a QA pass on a deployed environment, say) without the agent ever holding the password or the session:

- **The password** is a skill credential of type API key with **Sent in: Request body** and the login host. The skill's env var holds a placeholder; the agent puts it in the login form or the JSON it posts, and the proxy swaps in the real value, on that host only. It is encoded for the body's content type, so a `&` or a quote in the password can't break the form. Responses from that host are scrubbed of the password (as sent, URL-, JSON- and HTML-encoded), so a page that echoes the field back can't reveal it.
- **A TOTP code** (2FA through an authenticator app) is a second credential with **Sent in: TOTP code** on the same host. Its secret is the key the app shows when you set up 2FA ("can't scan the QR code? enter this key"), or the full `otpauth://` link. The agent types its env var into the 2FA field, and the proxy replaces it with the code current at that moment. The form shows the current code as soon as you paste the key, so you can finish setting up 2FA on the test account without a phone. The key never leaves the proxy.
- **Session cookies** reach the agent as placeholders. The proxy keeps the real value of every `HttpOnly` cookie and hands the browser a stand-in with the same attributes, swapping it back only on requests to a host that cookie would really be sent to. Cookies the page reads from JavaScript (CSRF tokens, OAuth `state`, flags) pass through unchanged. On responses to a request that carried a credential (an injected header, the password, or a session cookie), every cookie is vaulted.

The agent logs in like a user would, and logs in again whenever a session expires. Through the proxy, Chromium needs the proxy set explicitly and has to skip certificate checks, since it ignores `SSL_CERT_FILE`:

```python
import os
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch(proxy={"server": os.environ["HTTPS_PROXY"]})
    page = browser.new_context(ignore_https_errors=True).new_page()
    page.goto("https://app.example.com/login")
    page.fill("#email", "qa@example.com")
    page.fill("#password", os.environ["QA_PASSWORD"])
    page.click("button[type=submit]")
    page.fill("#otp", os.environ["QA_TOTP"])  # if the app asks for a 2FA code
    page.click("button[type=submit]")
```

Limits:

- **Tokens returned in a response body are visible to the agent.** A login API that answers with `{"token": "…"}` hands the agent that token. Prefer an app's cookie-based login where it has one.
- **The scrub matches the password as sent or plainly encoded.** A host that hands it back transformed (base64, hashed, split up) isn't caught, so don't give the agent an account on an app that does that.
- **Email, SMS and push 2FA** can't be automated. Give the test account an authenticator app (TOTP) instead.
- **The session is still a capability.** The agent can't read the password or the cookie, but it can act as that user. Use a dedicated, least-privilege account.

## Network Isolation

By default, agent containers have unrestricted network access. Restricting this is the most important hardening step.

Agent containers need to reach:
- `api.anthropic.com` (or your LLM proxy) for model calls
- `api.github.com` / `api.gitlab.com` for Git operations
- `sentry.io` for error context fetching

They do **not** need access to your database, Redis, or backend API.

JeanClode does **not** create any `NetworkPolicy` (or `CiliumNetworkPolicy`) on your behalf — the backend's Kubernetes RBAC role is scoped to Jobs and the pods, Secrets, and ConfigMaps that belong to them, nothing network-related. Egress restriction is entirely operator-managed, on purpose: a policy JeanClode auto-provisioned per Job would need to special-case every cluster's own admission rules (a centrally-managed CNI, an admission policy that rejects namespaced egress rules, a cloud provider that blocks the metadata IP itself), and would silently stop enforcing anything the moment it couldn't reconcile. See the [Kubernetes](/docs/deployment/kubernetes) guide for the plain `NetworkPolicy` example that restricts egress to only these external addresses.

## CI-Gated Fix Verification

Before the fixer agent can finalize its turn, [Sentry Fix](/docs/workflows/sentry-fix) and [Issue Resolve](/docs/workflows/issue-resolve) wait on the target repository's own CI to pass on the pushed commit — per repo, for an Issue Resolve fix that spans more than one (see [ADR-008](https://github.com/jeanclode-hq/jeanclode/blob/main/docs/adr/008-ci-gated-fix-verification.md)). This reads check/pipeline status only, never runs anything on your infrastructure, but it does mean the GitHub App needs a few extra **read-only** permissions beyond code and PR access:

- **Checks: Read** and **Commit statuses: Read**, to read CI results from both the Checks API (GitHub Actions, most third-party CI) and the legacy Status API
- **Actions: Read**, to pull failing-step logs so the agent knows what to fix
- **Administration: Read**, to read branch-protection/required-status-checks so a non-blocking check failure doesn't hold up the PR

GitLab needs no additional scope, the existing `api`-scoped access token already covers pipeline/job/trace reads.

## Webhook Verification

All incoming webhooks are verified by HMAC signature before processing:

- **GitHub**: `X-Hub-Signature-256` using the GitHub App webhook secret
- **GitLab**: `X-Gitlab-Token` using the GitLab webhook secret
- **Sentry**: `sentry-hook-signature` using the per-organization client secret

## Secrets Management

- Never commit `.env` to git
- Rotate `ENCRYPTION_KEY`, `ADMIN_SECRET`, and `OAUTH_STATE_SECRET` periodically
- In production, inject secrets from a secrets manager (AWS Secrets Manager, Vault, Doppler) rather than static environment variables

## TLS

Terminate TLS with a reverse proxy, never expose the backend or frontend ports directly. The backend has no `/api` prefix on its routes, so strip it at the proxy:

```
# Caddy
jeanclode.example.com {
  handle_path /api/* {
    reverse_proxy backend:8000
  }
  reverse_proxy frontend:3000
}
```

## Admin Page

The `/admin` page is rate-limited to 5 attempts per 15 minutes. In production, consider restricting it to your office IP at the reverse proxy level.
