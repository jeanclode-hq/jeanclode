## Overview

Every workflow run normally starts from zero — an agent that triaged a Sentry error as a known false positive last week re-discovers that from scratch this week. Agent memory fixes that: a workspace-scoped store that judgment-heavy agents can read from and write to, so what one run learns is still there the next time any agent runs against that workspace, potentially days later and in a completely different container.

This is durable, cross-run knowledge, not scratch state for a single run. Progress tracking, todo lists, and this-run notes belong in the agent's own reasoning and output, not in memory.

## What gets stored

Six operations, matching Anthropic's `memory_20250818` tool contract: `view`, `create`, `str_replace`, `insert`, `delete`, `rename`. An entry is a flat key-value pair (`path` → `content`) scoped by workspace — a repo is just a path prefix inside the store (`backend-repo/notes.md`), since one workspace can span multiple repos.

The test every agent applies before writing: *would an agent working on a different issue or PR act differently after reading this?*

Worth keeping:
- A correction a human made to a past review, fix or style choice
- A repo-specific gotcha: a flaky test, a CI quirk, a tool missing from the sandbox, a misleading error
- A Sentry error confirmed not actionable, keyed by its error signature
- A convention the repo follows that its docs don't state

Never written: logs of a run ("reviewed, no findings", rebase narration), notes about one PR that stop mattering once it merges, facts the code already states, unconfirmed guesses, secrets.

Entries follow a fixed layout: `<repo>/<topic>.md` for one repo, `_workspace/<topic>.md` for anything true across repos, and one `<repo>/sentry-known-noise.md` per repo for Sentry verdicts. Files are named after their topic, never after a PR or issue id, and kept under ~8,000 characters.

## Curation

Agents write memory on every run, so without pruning it fills with noise and duplicates. Once a day, the backend's memory plugin runs a **curator** on each workspace that has entries changed since the curator last saw them.

The curator is an agent with the memory tool and nothing else: no shell, no file access, no codebase. It judges each entry from its content alone, against the same rules the writers follow:

| Action | When |
|--------|------|
| Delete | Run logs, notes tied to one PR, facts the code states, guesses, entries a newer one supersedes |
| Merge | Two entries cover the same fact; per-issue Sentry verdicts fold into `sentry-known-noise.md` |
| Rewrite | A real lesson buried in a narrative; repeated sections; tokens, internal IPs or personal data |
| Move | A file named after a PR or issue, or knowledge true across repos that belongs under `_workspace/` |
| Keep | Everything that already follows the rules, and every human correction |

Deletion is a soft delete: the entry is kept in the database with a `deleted_at` timestamp and never served again, so a bad curation call never loses knowledge for good.

A run curates every due entry in batches of 20, each batch in a fresh session, and marks a batch curated only once its session finishes. A failed or rate-limited run leaves its entries due for the next one. Curator runs link no issue or PR, so they don't appear in the dashboard's execution list.

## Which agents use it

Memory is opt-in per agent, enabled only where independent judgment is worth remembering:

| Workflow | Agents with memory |
|----------|---------------------|
| Sentry Fix | Triage, Fixer |
| Issue Resolve | Triage, Fixer |
| Code Review | Analyzer, FactChecker |
| JeanClode Respond | Planner |
| PR Summary | none |

The rest don't get memory, because there's no independent judgment there worth recording: Synthesis, Synthesizer, Deduplicator and Styler merge or reformat what another agent already produced, and IssueExplorer just fetches the linked issues named in the PR description.

## Configuration

Memory is always on for every workspace — there's no flag to flip. Curation is on by default too; set `MEMORY_CURATION_ENABLED=false` to turn it off, or `MEMORY_CURATION_CADENCE_HOURS` to change how often it runs (default `24`). The signing secret that authenticates a container's memory calls (see below) is generated by the backend itself the first time it starts, and persisted so every replica shares it. No environment variable to generate or rotate.

The one thing that does need setting is [`BACKEND_URL`](/docs/configuration/environment-variables) — the backend's own address, reachable from agent containers. It has a working default under Docker Compose, but on Kubernetes there's no default and it must be set explicitly, since the backend can't infer how other pods reach it back. If it's missing, memory creds are silently skipped for every dispatch (a warning is logged, but the run itself doesn't fail) and agents get no memory tool that run.

## How it reaches a container

Sandboxed containers reach the memory API the same way they reach every other integration — through the security-proxy sidecar, never a direct connection. At dispatch time, the backend mints a short-lived (12-hour), HMAC-signed token scoped to the workspace and the specific execution, and hands it to the sidecar. The agent process never sees or constructs the `Authorization` header itself, the same as `gh`/`glab` credentials.

```
Dispatch: mint workspace-scoped token → sidecar
Container: agent calls memory tool → sidecar injects Authorization → backend
Backend: verifies token signature + expiry → scopes every query to workspace_id
```

Because `workspace_id` only ever comes from a verified token — never a client-supplied field — a compromised or prompt-injected agent can't reach a different workspace's memory by changing a request parameter.
