## Overview

Each workflow in JeanClode is self-contained, [Sentry Fix](/docs/workflows/sentry-fix) fixes an error, [Code Review](/docs/workflows/code-review) reviews a PR, [JeanClode Respond](/docs/workflows/jeanclode-respond) answers a mention. What makes the system autonomous is that **workflows trigger each other** by attaching `jeanclode:<workflow>` labels to PRs and issues. A label add is a webhook event, and a webhook event is a workflow trigger, so one workflow finishing its job can kick off the next one without a human in the loop.

## The label convention

Every git-triggered workflow is gated by a label of the same name:

| Label | Fires |
|-------|-------|
| `jeanclode:review` | [Code Review](/docs/workflows/code-review) |
| `jeanclode:summary` | [PR Summary](/docs/workflows/pr-summary) |
| `jeanclode:resolve` | [Issue Resolve](/docs/workflows/issue-resolve) |

Whether a given event dispatches a workflow depends on the org's trigger setting for that workflow:

| Setting | Dispatches on |
|---------|---------------|
| `manual` | nothing — dashboard or CLI only |
| `on_commit` | a new commit on the PR (`synchronize`) |
| `on_pr_creation` | the PR being opened |
| `on_label` | the label being added |
| `on_pr_creation_and_label` | the PR being opened *with* the label already on it, or the label being added later — **the default for review and summary** |

::warning
The loop below re-attaches `jeanclode:review` to send a pushed fix back through review, so it only runs on an org whose `review` trigger honors labels — `on_label` or the default `on_pr_creation_and_label`. Set `review` to `manual`, `on_commit` or `on_pr_creation` and the relabel is ignored, so the loop stops after the first round. `jeanclode:resolve` on an issue is the exception: it dispatches Issue Resolve regardless of trigger mode.
::

## The review loop

Every PR JeanClode opens runs the same loop, and it has exactly two exits.

```
Sentry Fix / Issue Resolve
  fixes the bug, CI-gates the commit, opens the PR
  │
  ▼ attaches `jeanclode:review` + `jeanclode:summary`
Code Review
  runs its 7-agent pipeline
  │
  ├─ findings remain
  │    │
  │    ▼ posts one `@jeanclode-bot` follow-up comment:
  │      "handle all the comments above — verify each isn't a false
  │       positive or already resolved first"
  │    │
  │    ▼
  │  JeanClode Respond
  │    per finding: it's real → fix it, then resolve the thread
  │                 it's not → resolve the thread, explain why
  │    │
  │    ├─ it pushed something
  │    │    │
  │    │    ▼ the workflow diffs origin's tip before/after the turn
  │    │  removes and re-adds `jeanclode:review`
  │    │    │
  │    │    └──────────────▶ Code Review runs again ──┐
  │    │                      against the new commit  │
  │    │  ◀─────────────────────────────────────────  ┘
  │    │
  │    └─ it pushed nothing, and that closed the last open thread
  │         → every finding was a false positive. No push, no relabel,
  │           no re-review, and no LGTM will ever arrive — so this is
  │           where the loop ends. ⟶ ready notice
  │
  └─ nothing left to flag → LGTM ⟶ ready notice
```

The follow-up sweep only ever fires on a PR whose author is the bot. That flag is the loop guard: a human's PR never gets swept, and the bot never mentions itself anywhere else.

### The ready notice

Both exits converge on the same thing: the people the org picked in its git integration settings get @-mentioned in a comment saying the MR is ready for them. See [Notifications](/docs/configuration/notifications) for how to set that list.

It's post-once. Both exits write the same invisible HTML-comment marker and check for it first, so whichever fires second stands down.

It's a comment, not the description, because [PR Summary](/docs/workflows/pr-summary) rewrites descriptions wholesale — a mention placed there wouldn't survive the next summary run.

The list is stored as provider identity ids rather than handles, resolved to handles at dispatch time against the org's own memberships. A rename can't stale it out, and someone removed from the org stops being notified.

## Mentions from humans

The same [JeanClode Respond](/docs/workflows/jeanclode-respond) workflow handles a human's `@jeanclode-bot` mention anywhere: an issue, a PR description, a review thread. The planner either handles the ask directly or routes it:

```
@jeanclode-bot please take care of this   (on an issue)
  │
  ▼ route: removes and re-adds `jeanclode:resolve`
Issue Resolve
  triages, implements, opens its own PR — one per repo touched
  │
  ▼ each PR gets `jeanclode:review`, entering the loop above
```

Respond never does the triage/fix work of another workflow itself. When a request needs that, it routes; that's an explicit rule in the planner prompt, not a hope.

### Why remove-then-add, not just add

`gh pr edit --add-label` and `glab mr update --label` are no-ops if the label is already present: no state change, no webhook. Both the post-push relabel and the `route` action strip the label and add it back, forcing a fresh `labeled` webhook event, which is what the backend's trigger evaluator listens for — regardless of whether the label was already sitting there from a previous round.

### Why this doesn't loop forever

- **The relabel is evidence-based.** It only fires when `origin`'s tip actually moved, checked with `git ls-remote` before and after the planner's turn. A turn that pushed nothing can't spuriously re-fire review, and the planner's own account of what it did is never what's trusted.
- **Findings shrink each round.** Code Review's Deduplicator and FactChecker keep a re-review from repeating findings that were already addressed or already discussed.
- **Termination is convergence, not a counter.** The loop stops when a review pass has nothing left to flag, or when a respond turn resolves the last thread without pushing. Both of those are the ready notice, which is also the signal a human should look.
- **There's no gate before a push**, deliberately. The planner decides whether a change is safe to push, the same judgment it applies to the rest of the ask. If it isn't confident, it can reply and explain instead.

## Where each workflow fits

- [Sentry Fix](/docs/workflows/sentry-fix), entry point for error-driven work. Ends by handing off to review.
- [Issue Resolve](/docs/workflows/issue-resolve), entry point for issue-driven work, either from issue-open triggers or from Respond's `route` when a mention expresses fix intent. Also ends by handing off to review.
- [Code Review](/docs/workflows/code-review), entry point for PR-driven work (it also fires directly on human-authored PRs). Its findings are the surface the loop turns on.
- [JeanClode Respond](/docs/workflows/jeanclode-respond), the decision point. Handles the ask directly, or routes it to whichever workflow actually owns real triage and implementation.
- [PR Summary](/docs/workflows/pr-summary), informational. It rewrites the description and doesn't feed back into the loop.

Because the handoff is just a label plus a webhook, adding a new self-triggering workflow doesn't require touching this loop, it only needs to attach the right `jeanclode:<workflow>` label when it's done.
