## Workflows, activities, agents

JeanClode is a set of **workflows**, each triggered by a different kind of event and each owning its own pipeline. A workflow is plain Python orchestration over two kinds of step:

- **Activities** are deterministic. Git operations, opening PRs, polling CI, posting comments, attaching labels, scanning for secrets, routing decisions. No model is involved.
- **Agents** are [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) sessions, each with its own prompt and a schema its output has to satisfy.

Anything that can be decided deterministically is an activity. Model calls are reserved for judgment, which is what makes a run's behavior auditable: a triage verdict is the model's, but what happens as a result of that verdict is code.

```
External event
  │
  ▼
Workflow (Python)
  │
  ├─ activity   deterministic — git, PRs, CI, posting, routing
  └─ agent      judgment — triage, analysis, fixing, summarising
```

### The pipelines

| Workflow | Pipeline |
|---|---|
| [Sentry Fix](/docs/workflows/sentry-fix) | fetch → parallel triage → deterministic filter/route → synthesis → one worktree + PR per target repo → one fixer session → CI gate → label |
| [Code Review](/docs/workflows/code-review) | IssueExplorer → 2× Analyzer (parallel) → Synthesizer → Deduplicator → FactChecker → Guardrail → Styler → post |
| [Issue Resolve](/docs/workflows/issue-resolve) | triage (findings double as the plan) → fixer → CI gate → PR per repo touched |
| [PR Summary](/docs/workflows/pr-summary) | Summarizer → Parser → rewrite the description |
| [JeanClode Respond](/docs/workflows/jeanclode-respond) | one planner agent acting directly, plus two deterministic post-turn checks |

### Why Multiple Agents?

A single "review this diff" or "fix this error" prompt leads to hallucinations. Splitting the work up:

1. **Parallel exploration**, independent agents with code search tools explore the codebase separately, finding issues a single pass would miss
2. **Adversarial fact-checking**, the FactChecker starts with fresh context and independently re-verifies every claim against actual code
3. **Structured handoffs**, each stage returns a schema, so the step after it can route deterministically instead of parsing prose
4. **High signal, low noise**, only findings that survive every filter are posted

### Deterministic guards on agent turns

Agents that write code run under hooks that a model can't talk its way past:

- A fixer can't end its turn without a real commit pushed on top of the run's base.
- A fixer can't end its turn until the repo's own CI is green on that commit, or there's no CI signal to gate on. A failure is fed back with the failing-step logs, bounded to six rounds.
- A GitLab reply has to stay inside the discussion the mention came from.

## System Architecture

```
External event
      │
      ▼
FastAPI backend (webhook ingestion, organization routing)
      │
      ▼
Redis queue (async dispatch via FastStream)
      │
      ▼
CLI worker (jeanclode)
      │
      ▼
Multi-agent pipeline (Claude Agent SDK)
      │
      ▼
GitHub / GitLab API  →  PR opened / comments posted
Sentry API           →  issue commented
```

Workflows don't just run once and stop, PRs and issues carry `jeanclode:<workflow>` labels that let one workflow hand off to the next (a fix hands off to review, a pushed fix re-triggers review, and so on). See [Autonomous Loop](/docs/architecture/autonomous-loop) for how that self-triggering works.

## Tech Stack

| Component | Technology |
|-----------|------------|
| **Backend** | FastAPI, SQLAlchemy, Alembic, FastStream |
| **Frontend** | Nuxt 4, Vue 3, Pinia, Nuxt UI, SSE |
| **AI Engine** | Claude Agent SDK — custom agents, prompts and output schemas per workflow |
| **Database** | PostgreSQL |
| **Queue** | Redis (via FastStream) |
| **Deployment** | Docker Compose / Kubernetes |

## Monorepo Structure

```
jeanclode/
├── backend/              # FastAPI API server
│   ├── api/              # Plugin-based architecture
│   └── configs/          # YAML config (docker.yaml, kubernetes.yaml)
├── cli/                  # Python CLI (jeanclode)
│   └── src/
│       ├── workflows/    # One package per workflow
│       ├── activities/   # Deterministic steps (git, CI, posting)
│       ├── agents/       # Agent definitions + output schemas
│       ├── prompts/      # Agent prompts
│       └── adaptors/     # Per-platform URL/auth/context handling
├── security-proxy/       # Credential injection sidecar
├── frontend/             # Nuxt 4 dashboard
├── packages/             # Shared TypeScript SDK (generated from OpenAPI)
├── website/              # This documentation site
└── docker-compose.yml
```

## Backend Plugin Architecture

The backend loads capabilities as plugins:

| Plugin | Responsibility |
|--------|---------------|
| `DatabasePlugin` | PostgreSQL connections, Alembic migrations, credential encryption |
| `WebServerPlugin` | FastAPI routes, sessions, admin page |
| `GitHubPlugin` | GitHub App OAuth, webhook verification, API client |
| `GitLabPlugin` | GitLab OAuth, webhook verification, API client |
| `SentryPlugin` | Sentry webhook ingestion, API client |
| `FastStreamPlugin` | Redis message broker, queue consumers |
| `ContainerPlugin` | Docker/Kubernetes job management, scheduled redispatch |
| `OAuthPlugin` | GitHub/GitLab OAuth for dashboard login |

Configuration lives in YAML files in `backend/configs/`. The plugin system enables composable deployments, run everything on one server, or split into separate worker pods.

## Admin Page

All provider credentials (GitHub App, GitLab OAuth, LLM credentials) are configured through `/admin` and stored encrypted in the database. No integration env vars are needed at deploy time.

LLM credentials are a **priority-ordered pool** rather than a single key: mix API keys and Claude subscription OAuth tokens, and dispatch walks them in order, skipping any that recently hit a rate limit. Work that finds every credential exhausted is deferred and redispatched once one frees up rather than failing. See [Model Configuration](/docs/configuration/model-configuration).
