## What it's for

A QA pass on a deployed environment, checking a page after a fix, reproducing a bug that only shows up when logged in. A skill says what to check ("log in to staging and screenshot the orders page"); the agent does it in a real browser, one step at a time, seeing the page after each action, so it handles a cookie banner, a 2FA step or an error page the way a person would.

## The browser

On an Issue Resolve run and on a `@jeanclode-bot` mention, the agents that do the work have a browser: the [Playwright MCP](https://github.com/microsoft/playwright-mcp), started with the run and driving a headless Chromium.

- It goes through the same proxy as everything else, so it only opens hosts some credential allows. Anything else fails with a tunnel error.
- Its profile lives in memory and disappears with the run.
- It's installed at the start of each run (pinned versions, a few seconds) from `nodejs.org` and `registry.npmjs.org`. If those are blocked, the run goes on without a browser and logs why.

The demo agent that records UI changes keeps its own, separate browser, which only reaches `localhost`.

## Setting it up

1. **A test account.** Create a dedicated, least-privilege account on the app. If the app uses an authenticator app for 2FA, keep the setup key ("can't scan the QR code? enter this key").
2. **The skill.** A `SKILL.md` that says where to go and what to check, and names the env vars it uses. For example:

   ```markdown
   ---
   name: staging-qa
   description: Log in to staging and check the orders page. Use when asked to QA or smoke-test staging.
   ---

   1. Open https://staging.example.com and log in as qa@example.com.
   2. For the password, type the value of $STAGING_PASSWORD as is.
   3. If a 2FA code is asked, type the value of $STAGING_TOTP.
   4. Open the orders page and take a full-page screenshot.
   5. Report whether the login worked and anything broken on the page.
   ```

   The env vars hold placeholders, not the real values, and that's what the agent should type. Put the email in the skill itself: an email field won't accept a placeholder.
3. **The credentials** on the installed skill ([details](/docs/skills-and-mcp/credentials)):

   | Env var name | Auth type | Sent in | Target host |
   |---|---|---|---|
   | `STAGING_PASSWORD` | API key | Request body | the login host, e.g. `login.example.com` |
   | `STAGING_TOTP` | API key | TOTP code | the login host |
   | (none) | No auth | | the app's host, e.g. `staging.example.com` |

   If the app loads things from other hosts the page needs (an API, a CDN), add a No auth entry for each. A run that hits one it can't reach reports the host.
4. **Ask for it.** Open an issue ("QA staging: log in and screenshot the orders page") and label it `jeanclode:resolve`, or mention `@jeanclode-bot` on a PR. The agent answers with what it found.

## Good to know

- **Email, SMS and push 2FA can't be automated.** Give the test account an authenticator app (TOTP) instead.
- **A 2FA field that only takes 6 characters** cuts the placeholder short when typed. Tell the skill to set the field's value directly instead (the browser tools can run a line of JavaScript on the page).
- **The agent can act as the account.** It never sees the password, the 2FA key or the session cookie, but anything that account can do, the agent can do. Keep its permissions minimal.
