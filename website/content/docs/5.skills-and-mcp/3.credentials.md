## How it works

Every run happens in a sandbox whose only way out is a proxy. You store a credential once, on an installed skill or an MCP server, and the proxy adds the real value to the requests going to that credential's host. The agent only ever holds a placeholder, so a prompt injection can make it misuse a session but never leak the secret itself.

The proxy also decides what's reachable: a run can only talk to hosts some credential names (plus GitHub or GitLab, Sentry and the LLM). Everything else is refused with `denied: host not in allowlist`.

## Adding an auth

**Integrations → your organization → Skills → an installed skill → Add auth**, or **Add auth** on an MCP server. Each auth has:

- **Auth type**: what's stored (below).
- **Env var name** (skills): the variable the skill reads, e.g. `WIKI_API_KEY`. Check the skill's own instructions for the name it expects.
- **Target host**: where the proxy injects the value. Required on a skill; on an MCP server it defaults to the server's own host.

## Auth types

| Type | Stored | What the proxy does | Skills | MCP |
|---|---|---|---|---|
| API key / JWT | A key | Sets it in a header (`Authorization: Bearer …` by default), or swaps it into a body, see **Sent in** | ✓ | ✓ |
| Basic auth | Username and password | Sets `Authorization: Basic …` | ✓ | ✓ |
| OAuth2 | Client id and secret, plus a username and password or a refresh token for those grants | Fetches a token from the token URL, refreshes it before it expires, sets it as a bearer token | | ✓ |
| No auth | Nothing | Lets the host through, adds nothing | ✓ | ✓ |

## Sent in (skills)

An API key on a skill can travel three ways:

- **Header** (default): the proxy adds the key to every request to the host. The env var holds a placeholder the skill can pass along, but the proxy replaces the header anyway. For APIs.
- **Request body**: for a login form or a login API. The env var holds a placeholder like `jcsecret_APP_PASSWORD_…`; the agent puts it in the form or the JSON it posts, and the proxy swaps in the real value, on that host only, encoded for the body's type so a `&` or a quote can't break it. Responses from that host are scrubbed of the value, so a page that echoes a field back can't reveal it.
- **TOTP code**: for a 2FA step. Paste the key your authenticator app would get (the "can't scan the QR code? enter this key" text, or the full `otpauth://` link). The agent types the placeholder into the 2FA field and the proxy replaces it with the code current at that moment. The form shows the current code as soon as you paste the key, so you can finish setting up 2FA on the account without a phone. The key never leaves the proxy.

## Hosts

- **Exact host**: `api.example.com`. Paste a URL and only its host is kept.
- **Wildcard**: `*.example.com` covers every subdomain, but not `example.com` itself, which needs its own entry.
- **Several auths on one host** are fine: a password and its 2FA code, a No auth entry, or keys in different headers. The proxy merges them into one rule. What's refused is two auths setting the **same header** on a host (the second would silently overwrite the first), or two auths with the **same env var name** on one skill.
- **A host with no secret** (a public API, a CDN, the site a login lands on) gets a **No auth** entry.

## Session cookies

Cookies a site sets also stay in the proxy. It keeps the real value of every `HttpOnly` cookie and hands the agent a stand-in with the same attributes, swapping it back only on requests to a host the cookie would really be sent to. Cookies page scripts read (CSRF tokens, OAuth `state`) pass through unchanged. On a response to a request that carried a credential, every cookie is kept back. So the agent can stay logged in, but it can't read or carry away the session.

## Limits

- **Tokens returned in a response body are visible to the agent.** A login API that answers `{"token": "…"}` hands the agent that token. Prefer an app's cookie-based login where there is one.
- **The scrub catches a secret as sent or plainly encoded** (URL, JSON, HTML), not transformed (base64, hashed).
- **The session is still a capability.** The agent can't read the password or the cookie, but it can act as that account. Give it a dedicated, least-privilege one.
- **OAuth2 isn't available on skills yet**, only on MCP servers.
