On GitLab Free, group webhooks are a Premium feature — so the one group token can't carry a webhook, and issue, comment and merge request events never arrive on their own.

Instead you do two things: an instance **system hook** so JeanClode notices new projects, and a **webhook on each project** for the actual events. JeanClode can create and maintain those project webhooks for you.

::note
This assumes you've already done [Step 1: OAuth application](/docs/integrations/gitlab#step-1-oauth-application), including setting the webhook secret.
::

---

## 1. Create a system hook

**Admin Area → System Hooks** (self-hosted only — needs instance admin).

| Setting | Value |
|---------|-------|
| URL | `https://your-api-domain.com/webhooks/gitlab` |
| Secret token | the webhook secret from Step 1 |
| SSL verification | enable if the URL is `https` |
| Trigger checkboxes | leave **all** unchecked (Push, Tag push, Merge request, Repository update) |

A system hook always reports project, group and member lifecycle events regardless of the checkboxes — and that's the only thing JeanClode wants from it: to notice when a **new project is created**. Without it, a repo created after you connect won't show up until someone hits **Sync repos** on the organization page.

::warning
Leave **Merge request events** off. The per-project webhooks (step 3) already carry those, and enabling both delivers every MR event twice.
::

---

## 2. Create a group access token

Your group → **Settings → Access Tokens**.

| Setting | Value |
|---------|-------|
| Role | **Maintainer** |
| Scopes | `api`, `read_repository`, `write_repository` |

The role has to be **Maintainer** because creating a project webhook over the API is a Maintainer-level action — and that's what step 3 does on your behalf.

See [Access token scopes](/docs/integrations/gitlab#access-token-scopes-reference) for what each scope is used for.

---

## 3. Connect and turn on project webhooks

On the **Integrations** page, add the GitLab organization with that token, and enable **Create project webhooks**.

With it on, every repo sync creates JeanClode's webhook — merge request, issue, confidential issue, comment and confidential comment events — on **every project the group owns**. It's matched by URL, so a re-sync never stacks duplicates, and it's put back into shape if someone edits its events.

It's a toggle you can flip any time from the organization detail page. Turning it **off** — or deleting the organization — removes that webhook from every project JeanClode created one on. The create and delete happen in the background; there's nothing else for you to do.

New projects created later are discovered by the system hook from step 1, then get their webhook on the next sync.

---

## Alternative: a Developer token, webhooks by hand

If you'd rather not hand JeanClode a Maintainer token, create a **Developer** token instead (same `api`, `read_repository`, `write_repository` scopes) and leave **Create project webhooks** off.

Then you create the webhook yourself on **every project — and every new project** — under **Settings → Webhooks**:

| Setting | Value |
|---------|-------|
| URL | `https://your-api-domain.com/webhooks/gitlab` |
| Secret token | the webhook secret from Step 1 |
| SSL verification | enable if the URL is `https` |
| Triggers | Merge request events, Issues events, Confidential issues events, Comments, Confidential comments |

Developer is all JeanClode needs at runtime — clone, push a branch, open merge requests, post comments. Maintainer only ever came in for managing the hooks.
