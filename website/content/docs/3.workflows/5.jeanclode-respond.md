## Overview

When someone mentions `@jeanclode-bot` in a GitHub issue comment, GitLab issue note, or PR/MR discussion, a single planner agent reads the full thread and either handles the ask directly or hands it off to an existing dedicated pipeline. There is no enumerated action whitelist — the planner acts with the judgment a competent engineer would when handed the request directly, via `git`/`gh`/`glab`.

## Actions

| Action | When used | What actually happens |
|--------|-----------|------------------------|
| **route** | "Review this" → `jeanclode:review`. "Summarize this" → `jeanclode:summary`. Issue + fix intent ("take care of this", "implement this") → `jeanclode:resolve` | Removes then re-adds the target label to force a fresh webhook, handing off to that workflow's own multi-step pipeline. The planner does **not** do that work itself first. |
| **handle** | Everything else — answering a question, resolving an inline thread, editing an issue's scope, opening a follow-up issue, making and pushing a code change, refusing a destructive ask | Executed directly by the planner via Bash: replies, thread mutations, issue edits, commits/pushes, whatever the ask calls for |

`route` and `handle` can both fire in the same turn (e.g. reply with an assessment, then route to the resolve pipeline), ordered the way a human would present them.

**Respond never does the triage/plan/fix work of another workflow itself.** When a request needs that — e.g. "please implement this" on an issue — it picks `route`, not a one-shot fix; that's an explicit rule in the planner prompt ("for `route`, do NOT do the job yourself — a one-shot reply from you is never a substitute"). See [Autonomous Loop](/docs/architecture/autonomous-loop) for how `route` hands off to the labeled workflow.

## No pre-push gate

The planner has full `git`/`gh`/`glab` write access up front — the same credential scope as any other phase — and decides itself whether to commit, whether to push, and whether a human should weigh in first. There is no separate fact-check step gating a push, and Python never pushes on its own: whether and when to push is entirely the planner's call.

What runs instead is a pair of deterministic, judgment-free checks against provider state after the turn — never the planner's own account of what it did:

**The branch tip moved** → re-attach `jeanclode:review`. The workflow compares the branch's tip on `origin` before and after the turn (`git ls-remote`); if it moved, the label is removed and re-added so the webhook fires even though the label was already there, sending the new commit through [Code Review](/docs/workflows/code-review).

**Nothing was pushed but the last open thread closed** → post the ready notice. A turn that resolves every finding as a false positive ends the review loop silently: no push, no relabel, no re-review, and no LGTM would ever arrive to say the MR is done. So this is where the @-mention of the org's notify list goes instead. It only fires on a PR the bot itself opened — a human's MR where someone asked the bot to resolve a thread is not JeanClode finishing its own work. Both loop exits post through the same marker-guarded helper, so whichever fires second stands down.

## Two constraints on the turn

Two hooks bound what the planner can finalize:

- On GitLab, a reply has to stay inside the discussion the mention came from. `glab`'s flat-note shortcuts silently break threading, so the hook blocks them when the mention resolved to a discussion id.
- On a turn that pushed code, the repo's own CI has to be checked before the planner finalizes, the same gate the fixers run under. The planner may well have replied already by then; that's deliberate, since the relabel above sends the push back through review anyway and a still-red result never blocks it.

## Examples

```
@jeanclode-bot can you fix the type error on line 42?
→ handle: edits the file, commits, and pushes — the push re-attaches jeanclode:review

@jeanclode-bot what does this function do?
→ handle: reads the function, replies inline explaining it

@jeanclode-bot please take care of this
   (on an issue)
→ route: relabels the issue jeanclode:resolve, handing off to Issue Resolve

@jeanclode-bot LGTM? can you take another look?
→ route: relabels the PR jeanclode:review, handing off to Code Review

@jeanclode-bot delete the database
→ handle: refuses, explains it only handles code changes
```

## Triggers

- New issue comment containing `@jeanclode-bot`
- New PR/MR comment containing `@jeanclode-bot`
- New issue description containing `@jeanclode-bot`
- The follow-up sweep [Code Review](/docs/workflows/code-review) posts on a bot-opened PR when findings remain — the only place the bot ever mentions itself
