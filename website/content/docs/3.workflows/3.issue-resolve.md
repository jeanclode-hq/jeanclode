## Overview

The Issue Resolve workflow picks up a GitHub Issue or GitLab Issue/Work Item and resolves it end-to-end: reads the issue, explores the codebase, writes the code, and opens a PR that resolves it — one PR per repo touched, for fixes that span more than one.

There's no separate planning stage — triage already reads the codebase to decide whether an issue is actionable, so its findings (root cause, relevant files, suggested approach) are handed straight to the fixer instead of being re-derived from scratch by a second agent.

## Pipeline

```
Issue event (opened / labeled)
  │
  ▼
Fetch issue (title, body, labels, comments, linked issues)
  │
  ▼
Triage (actionable? clear enough? in scope?)
  explores the codebase — including any repo group the issue's repo
  belongs to — and, for actionable issues, decides which repo(s) the fix
  needs and writes findings for the fixer
  │
  ▼
Worktree per target repo (siblings under one parent when there's more
than one), one fixer session spanning all of them
  │
  ▼
Per repo, as the fixer pushes to it (not before):
  Open its PR/MR → CI gate on that repo's own CI
    failure → feed it back to the fixer, retry (up to 6 rounds)
    pass / no CI configured / already broken on default branch → continue
  Then label it `jeanclode:review` + `jeanclode:summary`, green or not
  A target repo the fixer never touches gets no PR — not an error, just
  unused (triage's repo list is a prediction, not a guarantee)
```

### Repo groups

An issue's own repo isn't always where the fix belongs — a thin QA/wrapper repo may point at a linked implementation repo, or a fix may genuinely need both a backend and a paired frontend change. When repos are grouped (configured per organization), triage explores every repo in the group and lists the ones — beyond the issue's own repo, which is always included — that also need a change. Each one gets its own worktree, and, once the fixer actually pushes something there, its own PR/MR.

PRs are opened lazily, per repo, only once there's a real pushed commit to show — never speculatively ahead of the fixer doing any work. For a multi-repo fix this matters more than it sounds: opening N PRs upfront based on triage's prediction multiplies the risk of an empty or wrong PR sitting in a repo that turned out not to need a change.

## CI-Gated Fix Verification

For every repo the fixer pushes a real commit to, that repo's own CI has to pass — GitHub Checks/Status API or GitLab pipeline status, whichever the provider exposes — before the fixer is allowed to finalize its turn. A failure is fed back to the agent (check result plus failing-step logs) so it can fix and retry, bounded to six rounds. A repo with no CI configured, or a failure already present on the default branch, doesn't block: there's no signal to gate on. The runner independently re-verifies CI on the final commit rather than trusting the agent's own loop.

CI is a signal for the fixer to act on mid-session, not a gate on the PR. Once the fixer is done, every repo that received a real commit gets its PR labeled for review whether or not CI ended up green — the retry budget above was the chance to fix it, and a failure that survives it isn't grounds to leave the work unreviewed. The run reports an error only when the run itself broke: nothing pushed anywhere, or an exception. The CI outcome is still recorded per repo so you can see it.

See [ADR-008](https://github.com/jeanclode-hq/jeanclode/blob/main/docs/adr/008-ci-gated-fix-verification.md) and [Security Hardening](/docs/deployment/security-hardening) for the read-only permissions this requires.

## Triage Decisions

| Classification | Action |
|---------------|--------|
| Proceed | Implements the fix and opens a PR per repo touched |
| Anything else | Posts a comment on the issue explaining why — out of scope, unclear, already fixed, a duplicate of an existing issue or PR — and stops |

## Supported Issue Types

- GitHub Issues
- GitLab Issues
- GitLab Work Items (GraphQL API)

## Triggering

**Automatically**: on issue creation, or when `jeanclode:resolve` is attached — including by [JeanClode Respond](/docs/workflows/jeanclode-respond) when someone asks the bot to take care of an issue. Which of those applies depends on the org's `issue_resolve` trigger setting (defaults to manual). Requires the [Self-Hosted Platform](/docs/getting-started/admin-dashboard).

## PR Format

Branch: `fix/issue-{issue-number}-{hash}`, deterministic per issue — a retried run lands back on the same branch instead of opening a duplicate. The same branch name is reused across every repo in a multi-repo fix; each repo's PR is independent, but a reviewer can tell they belong to the same fix by branch name alone.

The PR body links back to the issue and, for a multi-repo fix, names the other repos also touched so a reviewer on one PR isn't confused why it looks incomplete on its own.

Every PR it opens is labeled `jeanclode:review` and `jeanclode:summary`, which hands it to [Code Review](/docs/workflows/code-review) and [PR Summary](/docs/workflows/pr-summary) and starts the review loop described in [Autonomous Loop](/docs/architecture/autonomous-loop).
