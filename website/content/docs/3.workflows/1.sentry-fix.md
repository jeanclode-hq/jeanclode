## Overview

JeanClode collects incoming Sentry issues per tenant in a **batch window**, up to 5 issues every 5 minutes, and dispatches the whole batch to a single container. Each issue is triaged independently, related issues are grouped by root cause, and each group goes through its own fix → PR cycle.

## Pipeline

```
Batch window (per tenant, up to 5 pending issues, every 5 min)
  │
  ▼
Fetch error context, one per issue
  (stack trace, breadcrumbs, tags, affected files, release)
  │
  ▼
Parallel triage, one agent per issue, run concurrently
  reads the source, decides which repo(s) the fix belongs in,
  and writes the findings the fixer implements
  │
  ▼
Filter + route (deterministic)
  actionable? no existing PR? not previously rejected? repo resolved?
  │
  ├─ none actionable ──────────────▶ stop, nothing to do
  │
  ├─ exactly one actionable ───────▶ single group
  │
  └─ multiple actionable ──────────▶ Synthesis agent
                                       groups issues that share a root cause
  │
  ▼
Per group (in parallel):
  one worktree + one PR per target repo, on one shared branch
  │
  ▼
One fixer session across every worktree in the group
  │
  ▼
CI gate: the repo's own CI on the pushed commit
  failure → feed the result and failing-step logs back, retry (up to 6 rounds)
  pass / no CI configured / already broken on the default branch → continue
  │
  ▼
Per repo: attach `jeanclode:review` + `jeanclode:summary`
  a repo the fixer never touched has its PR closed instead
```

### Phase Details

**Fetch**, Pulls the full error event from the Sentry API for each issue in the batch: exception type, message, stack trace, breadcrumbs, release version, environment, affected users.

**Parallel Triage**, One agent per issue, run concurrently across the whole batch. Triage is also the planner: it reads the affected source to confirm the bug exists in the current code, decides which repo(s) the fix belongs in, checks for PRs that already address the issue, and writes the findings the fixer will implement. There is no separate planning agent, triage has to read the code to reach a verdict at all, so those findings capture that investigation rather than paying a second agent to re-derive it from a prose summary.

**Filter + Route**, A deterministic step (no LLM) drops issues that aren't actionable, already have an open or merged PR, were previously rejected by a human, or whose target repos don't resolve to a checkout on disk. Repos are resolved by **name** against what's actually cloned, never by a URL the model supplied. Zero survivors stops the run; exactly one goes straight to a single-issue group; more than one goes to synthesis.

**Synthesis**, Only runs when multiple issues survive filtering. An agent partitions them into groups that share a root cause, so a bad deploy that fires 4 related errors produces one PR, not four. It returns the partition only, every other field (target repos, findings, affected files) is rebuilt from the triage records it grouped, so a reworded or invented repo name can't reach the code that opens PRs. Issues it omits become their own group rather than being dropped.

**Per-group Fix**, Each group gets one branch. Every target repo gets its own git worktree on that branch and its own PR, opened before the fixer runs so the live feed has a link immediately and each repo's CI has a merge request to run pipelines against. PRs are opened **ready, never as a draft**: a `Draft:` title makes GitLab skip the pipeline under a `workflow: rules` guard, and un-drafting isn't itself a pipeline trigger, so the MR would sit blocked on a pipeline that could never be created. Then a single fixer session runs across all of the group's worktrees. Groups run in parallel and don't block each other.

**CI Gate**, Before the fixer can finalize its turn, it must push a commit for which the target repo's own CI passes (GitHub Checks/Status API, or GitLab pipeline status). A failure feeds the check result and failing-step logs back to the agent so it can retry, bounded to six rounds. A repo with no CI configured, or a failure that's already red on the default branch, doesn't block, there's no signal to gate on. The runner independently re-verifies CI on the final commit, it never just trusts that the agent's own loop passed. See [ADR-008](https://github.com/jeanclode-hq/jeanclode/blob/main/docs/adr/008-ci-gated-fix-verification.md) and [Security Hardening](/docs/deployment/security-hardening) for the permissions this requires.

**Label for review**, Every repo that received a real pushed commit gets `jeanclode:review` and `jeanclode:summary` attached, whether or not CI ended up green. The gate above already gave the fixer its retry budget; a failure that survives it isn't grounds to leave the work sitting unreviewed. The `jeanclode:review` label is what hands the PR to the [Code Review](/docs/workflows/code-review) workflow, see [Autonomous Loop](/docs/architecture/autonomous-loop) for the full handoff. A target repo the fixer turned out not to need has its PR closed with a comment rather than left sitting empty.

## Fixes that span repos

Triage names every repo a fix needs, not just the one the Sentry event points at, and a fix that spans a backend and a paired frontend gets a PR in each. All of them share one branch name, so a reviewer on one PR can tell which others belong to the same fix, and each PR body names its siblings.

## Triage Decisions

| Classification | Action |
|---------------|--------|
| **Proceed** | Included in filter + route, proceeds toward a group |
| **Not actionable** | Filtered out, no PR opened |
| **Duplicate** | An open PR/MR already covers it, filtered out |
| **Already fixed** | A merged PR/MR already covers it, filtered out |
| **Previously rejected** | A PR fixing this root cause was closed unmerged, a human declined it, so re-proposing is worse than doing nothing |

JeanClode never opens duplicate PRs for the same Sentry issue, and never opens more than one PR per synthesized root cause per repo.

## Batching

- Each tenant gets its own 5-minute dispatch window; a window is skipped if the tenant was already dispatched in the last 5 minutes.
- Each batch is capped (default 5 issues). Overflow issues stay pending and are picked up in a later window.
- Issues that arrive in a later window but relate to an in-progress PR are evicted during triage, the open PR is what the next window's triage sees and deduplicates against, so staggered related errors still collapse into one PR.

## Rate limits

When every configured LLM credential is exhausted, the batch isn't lost: the issues stay `pending` and the next dispatch tick picks them up once a credential's window resets. A run that hits a rate limit part-way through has its leftover PRs closed and their bodies scrubbed of the identifying Sentry links first, otherwise the next triage would match them and treat the issue as already handled. See [ADR-010](https://github.com/jeanclode-hq/jeanclode/blob/main/docs/adr/010-llm-credential-failover-and-rate-limits.md).

## Triggering

**Automatically**: when a Sentry webhook fires for a new or regressed issue, via the [Self-Hosted Platform](/docs/getting-started/admin-dashboard).
